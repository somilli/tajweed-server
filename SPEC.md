# Sabaq tajweed-check server — API spec

Version 1.0.0 — Nov 12, 2026. The server is the **judge** in the
Sabaq ear. It does not track where the learner is in the verse (that
is Tilawi's job, on-device in the app) and it does not decide what the
learner should be saying (that is the reference QPS below). It answers
one question: **was this recitation of this verse correct, and where
exactly was it wrong?**

## Model

- **Quran Muaalem v3.2** (`obadx/muaalem-model-v3_2`, 2.42 GB,
  Hugging Face). **Hafs only** — no Warsh. Batch only, 16 kHz mono,
  max 30 s clips. One forward pass per request; the server derives
  both the predicted QPS and the CTC log-probs from that one pass.
- **License QML 1.0** (the `license:mit` tag on Hugging Face is
  WRONG — the GitHub LICENSE file is authoritative). Commercial use is
  allowed, but see **App-side obligations** below — the app must show
  the AI-advisory notice and offer a free/hardship path before any
  payment. Whether QML 1.0 permits shipping a fine-tuned derivative
  is UNKNOWN — check the LICENSE text before distributing
  fine-tuned weights.

## Endpoints

### GET /health

No auth. Returns:

```json
{
  "status": "ok",
  "model": "obadx/muaalem-model-v3_2",
  "model_load_s": 10.4,
  "uptime_s": 1234.5,
  "auth_required": true
}
```

`status` is `"loading"` until the model is in memory (~10 s after
start). `model_load_s` is null while loading.

### POST /check

Multipart form: `file` (audio, wav/m4a/mp3/ogg — decoded with
ffmpeg to 16 kHz mono), `surah` (1–114), `ayah` (int).
Header: `X-API-Key` — required when `TAJWEED_API_KEY` is set on the
server (setup.sh always sets one). No key set = no auth (dev only).

Limits: file ≤ 5 MB (413), audio 0.5–30 s (400 outside that range),
surah 1–114 and a real verse (400 otherwise). One inference runs at
a time; a second request waits up to 120 s, then gets 503.

Success (200):

```json
{
  "verse": "5:109",
  "uthmani": "يَوْمَ يَجْمَعُ ...",
  "duration_s": 8.42,
  "inference_s": 5.9,
  "rtf": 0.7,
  "model": "obadx/muaalem-model-v3_2",
  "reference_qps": "يَومَ يَجمَعُ ...",
  "predicted_qps": "يَومَ يَجمَعُ ...",
  "duration_info": {"harakah_s": 0.12, "pace_gap_frames": 3.0},
  "sites": [
    {
      "id": "site_1",
      "rule": "qalqalah",
      "label": "qalqalah on ج in يَجْمَعُ",
      "word": "يَجْمَعُ",
      "expected": [1],
      "model_measured": 1,
      "model_raw_run": 1,
      "model_verdict": "correct",
      "duration_beats": null,
      "duration_verdict": null,
      "verdict": "correct",
      "feedback": "Qalqalah on ج sounds right."
    }
  ],
  "summary": {"n_sites": 15, "n_error": 0, "n_uncertain": 7, "n_correct": 8},
  "advisory_en": "This feedback is generated by AI. ...",
  "advisory_ar": "هذه الملاحظات مولّدة بالذكاء الاصطناعي ..."
}
```

- `sites` — one entry per tajweed rule site in the verse, in reading
  order. `rule` is one of: `madd_normal`, `separate_madd`
  (munfasel), `madd_muttasel`, `madd_lazim`, `madd_aared`,
  `noon_moshaddadah`, `meem_moshaddadah`, `noon_mokhfah` (ikhfaa),
  `qalqalah`.
- `expected` — the valid set for the rule, e.g. aared `[2, 4, 6]`
  (the permanent waqf rule: verse-final madd may be 2, 4 or 6).
- `model_measured` — what the model heard, categorised into the
  rule's units (beats for madd, 1/0 for ghunnah/qalqalah, 2/1/0 for
  ikhfaa). `null` = the site could not be read from the model's
  output (word dropped or mangled) — that is an `uncertain`, never
  a guess.
- `model_raw_run` — the raw run length in the predicted QPS before
  categorisation (for debugging; `null` when unmeasurable).
- `model_verdict` / `duration_verdict` / `verdict` — each is
  `correct`, `error` or `uncertain`. `duration_*` is only filled
  for `separate_madd` sites; it is `null` for every other rule.
- `feedback` — a plain-language string for the verdict, ready to
  show or to map to the app's own wording.
- `summary` — counts over `sites`; the three counts always add up
  to `n_sites`.
- `advisory_en` / `advisory_ar` — the QML 1.0 advisory notice. The
  app must show it before first use (see below); the server also
  returns it on every check so the app can never lose it.

## How a verdict is reached

1. **Reference.** The verse's Uthmani text is phonetised
   (quran-transcript, Hafs) into a QPS string. The reference QPS
   already encodes every rule site — madd letters repeated per beat,
   shaddah as a doubled consonant, ikhfaa noon written ں, qalqalah
   marked ڇ — so no hand list of letters is needed. `find_sites()`
   walks the QPS and classifies each madd run: aared = last word +
   tail of exactly one consonant; munfasel = word-final run + next
   word starts with ء; mottasel = mid-word run + ء; lazim = mid-word
   run + doubled consonant; otherwise normal.
2. **Model.** One Muaalem forward on the audio. The predicted QPS
   comes from the same greedy decode the package uses, and the CTC
   log-probs (log_softmax of the phoneme logits, ~25 fps) are kept
   for the duration check.
3. **Measurement.** The predicted QPS is aligned to the reference
   with Levenshtein alignment (substitution cost 2, insert/delete 1
   — a wrong letter is a delete+insert, not a free relabel), plus an
   anchor-consistency check and a qalqalah tail fallback. Against
   the 159-clip qdat_bench set this reproduces the reference
   parser on **99.7% of 1,431 site measurements** (4 known
   deviations, 0.3% — see `tests/test_parser_regression.py`; two of
   the four are cases where this parser is MORE correct than the
   reference parser).
4. **Duration check (Rule B) — separate madd only.** The CTC
   alignment's frame span for the madd run, divided by the clip
   pace (median gap between phoneme peaks), gives beats. Verdict:
   within 0.5 beats of a valid length → `correct`; more than
   0.5 + 0.75 beats away from every valid length → `error`;
   in between → `uncertain`. Params are the calibrated modal values
   (delta 0.5, grey 0.75, no cap) from `qdat-bench/calibration.py`.
5. **Three-way gating.** `uncertain` is never shown as a correction.
   For separate madd: both error → error; model error + duration
   correct → uncertain; model error + duration uncertain → error;
   model correct + duration error → uncertain; both correct →
   correct; model correct + duration uncertain → uncertain; model
   uncertain → uncertain. Every other rule uses the model verdict
   alone (duration is not a judge there).

## Honest numbers (qdat_bench, 159 real learner voices, 5:109)

These are the numbers the app should be designed around — not the
paper's benchmark, the behaviour on real learners:

| What | FP rate | Detection | Notes |
|---|---|---|---|
| Whole system, all 9 rules | 4.8% | 57.7% | accuracy 88.8%; errors lean safe (101 missed vs 56 false) |
| Letter errors | — | 100% recall | the model never misses a real letter error; but it flags 82 correct words too (precision 25%) |
| Separate madd, model alone | 4.4% | 4.3% | it hears the rule, not the slip — 22 of 23 real errors normalised to a valid length |
| Separate madd, Rule B (this server) | 4.8% | 18.4% | ~1 in 5 real errors caught (~4× the model); **~41% of separate-madd verdicts land `uncertain`** — "not sure" must be designed as a common, normal outcome, never a hard correction |
| Madd aared | 6.0% FP | 0% | only 2–3 real errors in the 159 set — **no duration verdict for aared**; model only |
| Qalqalah | 10.9% FP | 96.6% | highest FP of any rule; a hand-rolled detector was tested and does NOT work (67% = baseline) |
| Ghunnah (noon/moshaddadah) + ikhfaa | 0.0% FP | 64% / 48% | the cleanest rules in the system |

**Do not ship as a bare flagger.** About 1 in 20 corrections is
wrong, and on separate madd the model alone catches 1 in 23 real
errors. The gating above is what makes it shippable: wrong
corrections are pushed to `uncertain` and shown only as soft
feedback ("try again / ask your teacher").

## App-side obligations (not optional)

1. **QML advisory, before first use.** Show the advisory text
   (returned as `advisory_en` / `advisory_ar` on every check) before
   the learner's first check, reachable from the main menu, in every
   UI language AND always in Arabic. It says the feedback is AI,
   may be wrong, is assistance only, is not a replacement for a
   proficient authorised teacher, and that the Quran is received
   only through oral transmission.
2. **Free / hardship path, before any payment.** Free access for
   those who cannot pay — automatic for World Bank low and
   lower-middle income countries (including Mali) plus a simple
   self-declaration / community-code path visible BEFORE any payment
   screen. The $60/mo price needs this path live before the checker
   ships.
3. **Only submit complete recitations.** The server checks every
   site in the verse. If the learner stops halfway, the unrecited
   sites come back `uncertain` (or `error` if the model hallucinates
   them) — that is not a finding, it is missing coverage. Coverage
   (did they finish the verse, which word are they on) is Tilawi's
   job on-device; do not send a partial attempt to this server and
   treat the result as a grade.
4. **Do not treat `uncertain` as a correction.** It means "not
   sure" — soft feedback only, never a red mark, never counted
   against the learner.

## Known gaps (carried honestly, not hidden)

- **Madd lazim is model-only and NOT validated** — 5:109 has no
  lazim, so the 159-set numbers say nothing about it. Same for
  **meem shaddah**: it uses the same ghunnah rule as noon shaddah
  but was not separately validated.
- **Ikhfaa is scored strict** (valid {2} only). A lenient view
  ({1, 2}) exists in the research; the server uses strict.
- **1:7 phonetizer quirk.** In Al-Fatiha 1:7 the phonetizer drops
  the alif of ولا before الضالين (`وَلَا ٱلضَّآلِّينَ` →
  `وَلَ ضضَاااااا...`), so that madd has no site and is never
  checked for 1:7. The model was trained on the same phonetizer
  output, so it omits it too — no false flag, just a gap.
- **Parser residuals (0.3%).** Four known deviations vs the
  reference parser on the 159 set, documented in
  `tests/test_parser_regression.py` (one heavily-mangled clip loses
  a site; one false positive in that same clip; two cases where this
  parser is more correct). Below the system's own 4.8% FP rate.
- **Tilawi is NOT a second opinion for letter errors** (tested Nov
  12 on the same 159 clips — it says "correct" on 97.6% of the
  model's false flags AND 92.6% of its true flags). Tilawi's role
  is recognition only: verse ID, follow-along, coverage.
